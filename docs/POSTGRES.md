# PostgreSQL and Supabase setup

## Connection

CleverSQL accepts a standard PostgreSQL URL:

```bash
node bin/cleversql.js \
  'postgresql://user:password@host:5432/database?sslmode=require' \
  --schemas public
```

For Supabase, copy the database connection string from the project settings.
The session pooler and direct connection strings both work. Keep
`sslmode=require`.

```bash
export SUPABASE_DB_URL='postgresql://postgres.<project>:<password>@<host>:5432/postgres?sslmode=require'
node bin/cleversql.js "$SUPABASE_DB_URL" --schemas public
```

Do not paste a service-role API key here. CleverSQL needs a PostgreSQL
connection string, and it should belong to a dedicated database role.

## Recommended role

Start with a role that can read the exposed schema and only write the tables the
agent is allowed to mutate.

```sql
CREATE ROLE cleversql_agent LOGIN PASSWORD 'replace-with-a-strong-secret';

GRANT CONNECT ON DATABASE your_database TO cleversql_agent;
GRANT USAGE ON SCHEMA public TO cleversql_agent;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO cleversql_agent;

-- Grant writes explicitly, table by table.
GRANT INSERT, UPDATE, DELETE
  ON TABLE public.customers, public.subscriptions
  TO cleversql_agent;

GRANT USAGE, SELECT
  ON ALL SEQUENCES IN SCHEMA public
  TO cleversql_agent;
```

A template is available at
[`scripts/postgres-role.sql`](../scripts/postgres-role.sql).

Do not grant:

- schema creation;
- table or index DDL;
- role administration;
- superuser;
- broad read access to schemas outside the allowed scope.

## Why the role still matters

CleverSQL blocks raw write SQL on its read surface, requires previews, and checks
for row drift before apply. It is an application-layer safety boundary, not a
replacement for least-privilege database credentials.

If an attacker gets the PostgreSQL DSN directly, database permissions become the
final boundary. Use a scoped role and rotate credentials.

## Transaction behavior

### Read queries

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
SET LOCAL statement_timeout = 15000;
-- wrapped user query with a hard row cap
ROLLBACK;
```

The connection transaction is explicitly read-only. PostgreSQL still permits
some side-effect functions, so treat the database role as the real authority.

### Governed changes

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SET LOCAL statement_timeout = 15000;
-- select before rows
-- in-place dry run
ROLLBACK;             -- preview
```

Apply and revert use the same transaction shape, but commit after the row hash
check passes. A serialization failure or a changed before-state returns a
conflict rather than overwriting newer work.

## Identity columns

CleverSQL supports common PostgreSQL schemas:

- `serial` / `bigserial`;
- `GENERATED BY DEFAULT AS IDENTITY`;
- `GENERATED ALWAYS AS IDENTITY`.

Normal inserts omit identity columns. Rollback of a deleted row uses
`OVERRIDING SYSTEM VALUE` so the original primary key can be restored.

## Schema scope

`--schemas public` exposes only the public schema.

Use `--schemas app,audit` for multiple schemas, or `--schemas all` to expose all
non-system schemas. Narrow scope is strongly recommended.

## Current limitations

- No row-level policy engine yet.
- No team SSO or per-user database credentials.
- No DDL or migration preview.
- No PostgreSQL `LISTEN/NOTIFY` integration.
- No distributed lock across multiple CleverSQL processes.

Use `--read-only` when connecting to a database that should never be mutated.
